# Review pack — sql-migrations

Detect: a migrations folder (`migrations/`, `db/migrate/`, `alembic/versions/`, `prisma/migrations/`, `database/migrations/`, `*.sql` with DDL), or ORM schema files (`schema.prisma`, models with schema changes, entity definitions) in the diff; for document stores, schema validators, index definitions, or aggregation and update code touching MongoDB-style collections.

Applies on top of core.md (its rule 8 covers destructive migrations; this pack adds the deployment and locking mechanics); project rules still win. First find the project's migration tool and its conventions (online-DDL helper, safety linter, `disable_ddl_transaction`, expand/contract policy), and judge the change against them.

## Critical

1. **Column or table removed or renamed while running code still uses it.** Mechanism: during a rolling deploy, old application instances run against the new schema. `DROP COLUMN`, `RENAME COLUMN`, `RENAME TABLE` or a type change in the same release as the code change breaks every old instance (and the rollback). Correct: expand and contract: add the new column, dual-write and backfill, switch reads, and drop only in a later release once no running code references it. Verify by grepping for the old name in the code that ships with the same deploy.
2. **Cascade delete reaching more than intended.** Mechanism: `ON DELETE CASCADE` (or ORM `cascade: all`, `dependent: :destroy`) on a foreign key to a table that holds financial records, audit logs or other tenants' history means deleting one parent row silently erases them, and a bulk delete multiplies this. Correct: `RESTRICT`/`NO ACTION` plus soft delete or an explicit archive step, unless the child is purely owned data. Name the child table and what is lost.

## High

3. **NOT NULL column without a default on an existing table.** Mechanism: `ADD COLUMN x NOT NULL` with no default fails outright on a non-empty table; with a volatile default, or on older engines (MySQL before 8.0 instant DDL, PostgreSQL before 11), it rewrites the whole table under an exclusive lock. Correct: add nullable, backfill in batches, then add the constraint (in PostgreSQL via `ADD CONSTRAINT ... NOT VALID` and `VALIDATE CONSTRAINT`), or a constant default on an engine that stores it as metadata. Check the engine and version in the project.
4. **Index creation that locks writes.** Mechanism: in PostgreSQL, plain `CREATE INDEX` blocks writes to the table for the duration of the build; on a large table this is an outage. Correct: `CREATE INDEX CONCURRENTLY`, which cannot run inside a transaction, so the migration must disable its wrapping transaction (`disable_ddl_transaction!`, `atomic = False`, `-- +goose NO TRANSACTION`, `CREATE INDEX CONCURRENTLY` via the tool's equivalent). A failed concurrent build leaves an invalid index that must be dropped. In MySQL check the tool uses `ALGORITHM=INPLACE, LOCK=NONE` or an online-schema-change tool. Same for `ADD FOREIGN KEY` and `ADD CHECK` (use `NOT VALID`).
5. **Data backfill in the same migration or deploy as the schema change.** Mechanism: an `UPDATE` over a large table inside the DDL migration holds locks and one huge transaction (replication lag, bloat, a deploy that times out and half-applies on engines without transactional DDL). Also couples the schema release to data volume. Correct: a separate, batched, resumable job (by primary key range, with a pause between batches) and a migration that only changes the schema.
6. **Long transaction or lock-heavy statement in a migration.** Mechanism: DDL waits for a table lock behind any open transaction and, while waiting, queues every later query behind it, so a blocked `ALTER TABLE` can take the service down. Spot DDL on a hot table with no `lock_timeout`/`statement_timeout`, or several heavy operations bundled into one transaction. Correct: set a short `lock_timeout` and retry, one risky operation per migration.
7. **New query or foreign key without a supporting index.** Mechanism: a new `WHERE`, `JOIN`, `ORDER BY` or a new foreign key column on a table that grows leads to a full scan; a missing index on the child side of a foreign key also makes parent deletes and updates scan the child table (and lock). Match the index to the query's column order (equality columns first, then range or sort). Report only where the table is clearly large or unbounded, and name the query. Document stores: the same for a new `find` filter, `sort` or `$lookup` field; check the compound index's field order against the query shape (a sort without an index can also fail on the in-memory limit).
8. **Uniqueness enforced only in application code.** Mechanism: `exists?` then `insert` (validates-uniqueness, find-or-create, `get_or_create`) races between concurrent requests and produces duplicates; the migration adds the column but no `UNIQUE` index. Correct: a unique index or constraint (partial or composite for soft delete and tenant scopes) with the code handling the violation as an expected outcome. On a table that may already hold duplicates, the migration must deduplicate first or the index build fails mid-deploy.
9. **Enum or type change that is not backward compatible.** Mechanism: removing or renaming an enum value, narrowing a column type or length (`varchar(255)` to `varchar(50)`, `bigint` to `int`), or changing a column's meaning fails on existing rows or breaks old instances. In PostgreSQL, `ALTER TYPE ... ADD VALUE` cannot be used in the same transaction as its first use on older versions, and a value cannot be removed at all. Correct: additive changes only, a lookup table or a check constraint for volatile value sets, and an expand/contract path for the rest.
10. **Down migration or rollback that loses data or fails.** Mechanism: a `down` that drops the column the `up` just filled, or is empty while the tool or team relies on rollback. Apply only if the project expects reversible migrations; otherwise the right fix is a documented forward-only note.

## Document stores (MongoDB and similar)

11. **Read-modify-write instead of an atomic operator.** Mechanism: `find` then `save`/`replaceOne` with a modified copy overwrites concurrent changes to the same document (a counter, a balance, an array). Correct: `$inc`, `$push`, `$addToSet`, `$set` on specific paths in `updateOne`, or a version field in the filter with a retry on no match. Complements core rule 4 for document databases.
12. **Unbounded array or document growth.** Mechanism: an array that gets a `$push` on every event (comments, logs, history) grows toward the 16 MB document limit, makes each update rewrite and re-index a large document, and slows reads that fetch it whole. Correct: a separate collection with a reference, or a bounded array (`$push` with `$each` and `$slice`), or bucketing.
13. **Schema drift without a validator or migration.** Mechanism: code starts writing a new field, or changes the type of an existing one (string to number, scalar to array), while old documents keep the old shape, so reads that assume the new shape fail or silently skip documents (`$gt` on mixed types matches only the same type). Correct: tolerate both shapes in code until a batched migration has run, or add a schema validator with a defined action on existing documents.

## Medium

14. **Index added or removed with no accompanying query change**, or a duplicate or redundant prefix index (an index on `(a)` beside `(a, b)`) that adds write cost for no read gain. Name the existing index.
15. **Timestamps without a time zone or a consistent default** (`timestamp` versus `timestamptz`, a default set in application code instead of the database), so rows written by different paths disagree.

## Do not report

- `NOT NULL` without a default on a table the migration itself creates, or that is verifiably empty or tiny (a lookup table, a table added in the same release).
- Plain `CREATE INDEX` on a table created in the same migration, or in a project documented as having a maintenance window.
- A `DROP` of a column that earlier commits in the same pull request or an earlier released migration already stopped using and stopped writing; confirm the earlier step exists before staying silent.
- Large backfills that the project runs through its own batch tool or a one-off script outside the migration, even if the file touches many rows.
- Index naming, column ordering in `CREATE TABLE`, or foreign-key naming conventions.
- Transactional DDL wrapping on engines that support it (PostgreSQL) for ordinary, non-concurrent changes.
