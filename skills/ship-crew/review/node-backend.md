# Review pack — Node.js backend

Detect: `package.json` with `@nestjs/*`, `express`, `fastify`, `hono`, `koa`, `@trpc/server`, `bullmq`, `bull`, `prisma`, `typeorm`, `drizzle-orm` or `mongoose`; server entry points, controllers, routers, processors, schema/migration folders.

Applies on top of core.md and the TypeScript pack; the project's rules win. Find the project's own mechanism (global guard, middleware chain, validation pipe, transaction wrapper, queue module) before judging.

## Critical
1. **Guard registered on the wrong scope or in the wrong order.** Mechanism: a global guard/middleware that does not cover a new module, a per-route guard list that omits the auth guard, or a roles/permission guard running before authentication (it sees no user and either crashes or passes). In Express/Hono/Fastify, `app.use(auth)` mounted after a router lets earlier routes bypass it; in NestJS, guards in `APP_GUARD` run in provider order, and `@Public()`-style decorators skip everything. Spot: new routers/controllers, changed registration order, a public decorator added. Check what the guard returns when metadata is missing (core rule 3).
2. **Mongoose or ORM filter built from raw request objects.** Mechanism: passing `req.body`/`req.query` directly into `find`, `findOne`, `where` or `updateOne` lets a client send operators (`{"$ne": null}`, `{"$gt": ""}`) that bypass a password, token or ownership match; `update(req.body)` allows setting any field (role, ownerId). Spot: query filters or update documents taken from request objects without a schema cast. Correct: validate to primitives, pick allowed fields explicitly.

## High
3. **Async errors escaping handlers (Express 4, event emitters, timers).** Mechanism: Express 4 does not catch a rejected promise from an `async` handler or middleware, so the request hangs and the process may emit an unhandled rejection; the same for `async` callbacks to `setTimeout`, `EventEmitter.on`, queue `process` callbacks without a surrounding catch. Spot: `async (req, res)` in Express 4 with no wrapper or `express-async-errors`; fire-and-forget calls in handlers. Correct: the project's async wrapper or Express 5, try/catch with `next(err)`, a catch on detached calls. Check the Express version first.
4. **Validation layer drops or trusts fields.** Mechanism: NestJS `ValidationPipe` with `whitelist: true` silently strips properties with no decorator, so a newly added DTO field without a class-validator decorator never reaches the service (and without `forbidNonWhitelisted` the client gets no error); with `transform` off, DTOs are plain objects and `@Type` conversions never run; a zod/typebox schema not attached to the route validates nothing. Spot: new DTO fields lacking decorators, changed pipe options, routes with no schema. Correct: decorate every field, confirm the pipe/schema is wired to this route.
5. **Transaction misuse and side effects.** Mechanism: Prisma `$transaction([...])` / interactive `$transaction(async tx => ...)`: queries made on the global client inside the callback run outside the transaction; calls that wait on external APIs inside it hit the interactive timeout and roll back after the effect fired; TypeORM `manager` vs injected repository, Drizzle `db` vs `tx`, Mongoose without passing `{ session }` have the same flaw. Spot: use of the outer client inside a transaction body, emitted events/queue adds inside it. Correct: use only `tx`/`session`, do effects after commit (core rule 5).
6. **Connection pool exhaustion.** Mechanism: a new client instance (`new PrismaClient()`, `new Pool()`, `mongoose.connect`, Redis client) created per request, per job or in hot-reloaded modules multiplies connections until the database refuses; a transaction holding a connection while awaiting a slow external call starves the pool; a manual `connect()` not released in `finally`. Spot: client construction outside the app's single provider, `pool.connect()`/`queryRunner` without release on every path. Correct: reuse the shared client/provider, release in `finally`.
7. **Scheduled job or worker runs on every replica.** Mechanism: `@Cron`, `node-cron`, `setInterval` or a queue repeatable job registered at app startup executes once per instance, so with N replicas emails, charges or cleanups run N times; the same applies to in-process workers started in the web process and to migrations on boot. Spot: new cron/interval/repeatable job with no leader lock, single-instance flag, or queue-level dedupe (job id). Correct: the project's scheduler lock, a dedicated worker deployment, or deterministic job ids.
8. **Queue job handlers not safe to retry or lose data on failure.** Mechanism: BullMQ/Bull retries re-run the whole processor, so a non-idempotent step repeats; a processor that catches and returns marks the job completed despite failure; jobs with huge payloads or whole records (stale by the time they run) instead of ids; no `removeOnComplete/Fail` policy fills Redis. Spot: processors with try/catch that swallow, payloads containing full entities, missing attempts/backoff or dead-letter handling per the project's pattern. Correct: pass ids, make steps idempotent, rethrow so the queue records the failure.
9. **Env validated or read at import time.** Mechanism: `process.env.X` read at module scope (or config module that throws on import) runs before the config loader/dotenv, in tests, and in CLI scripts that import the module; a missing var becomes `undefined` coerced to the string `"undefined"` in URLs and keys, or crashes on first deploy. Spot: top-level `const x = process.env.X` outside the project's config service, `Number(process.env.PORT)` with no default check. Correct: read through the validated config provider, fail fast at startup with a clear message.
10. **Event names or queue/topic names as duplicated string literals.** Mechanism: an emitter/`@OnEvent`/`@Process`/pub-sub channel string that differs by one character from its counterpart silently never fires, and nothing errors. Spot: new or renamed event/queue/channel/job names; check that emitter and listener share one exported constant and the same payload type. Correct: a shared constant or typed event map.
11. **Streaming and backpressure.** Mechanism: reading a large file/response/export fully into memory (`readFile`, `await res.json()`, `Buffer.concat`) on a request path exhausts memory; `stream.write` return value ignored, or `pipe` without error handling leaves sockets and file descriptors open when the client disconnects; `pipeline` not used. Spot: file downloads, CSV exports, proxying. Correct: `stream.pipeline` with error handling, abort on client close.
12. **Mongoose lean results and hydration.** Mechanism: `.lean()` returns plain objects: no virtuals, getters, `toJSON` transforms, `id` alias, or instance methods, and `_id`/`Date`/`ObjectId` types differ from hydrated documents, so code or serializers expecting them break or leak fields the schema's `toJSON` would hide (password hash, `__v`). Conversely, returning hydrated documents without `select` leaks hidden fields. Spot: `.lean()` added or removed, results returned directly in responses. Correct: explicit `select`/DTO mapping on output.
13. **Request body, upload and rate limits.** Mechanism: a new route accepting uploads, bulk arrays or a public unauthenticated action with no body size limit, array length cap or rate limit lets one client exhaust memory or send mail/SMS at will; a `trust proxy` setting wrong behind a load balancer makes IP-based limits apply to the proxy. Spot: new public endpoints or upload handlers outside the project's limiter. Correct: use the project's limiter/throttler and size limits.

## Medium
14. **Shutdown and lifecycle.** Mechanism: no handling of SIGTERM, or `enableShutdownHooks` missing, drops in-flight requests and jobs on deploy; workers not closed leave stalled jobs. Spot: new long-lived resources (workers, consumers, servers) with no close hook. Correct: close in the project's lifecycle hook.
15. **Error responses leaking internals.** Mechanism: raw ORM or driver errors (with SQL, table names, stack traces) returned to clients via a default error handler or `res.json(err)`; wrong status codes (500 for validation, 200 with an error body). Spot: custom catch blocks that serialize `err`. Correct: map to the project's exception filter/error format.

## Do not report
- Missing DTO decorators on fields that are intentionally internal and never come from clients.
- `any` in framework glue, decorator metadata, or ORM raw-query results where the project allows it.
- Per-route guards when a global guard demonstrably covers the route and the project's convention relies on it.
- Missing `await` on a deliberate fire-and-forget that has its own catch.
- N+1 concerns on admin/CLI scripts or bounded lists of a few items.
- Prisma/Drizzle generated client types absent from the checkout, and migration SQL files produced by the tool.
- Choice of framework, layering (controller/service/repository) or file naming as taste.
