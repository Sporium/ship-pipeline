# Review pack — CI/CD and infrastructure as code

Detect in the diff: `.github/workflows/`, `.github/actions/`, `.gitlab-ci.yml`, `Dockerfile*`, `docker-compose*.yml`, `.dockerignore`, `*.tf` / `*.tfvars`, Pulumi programs, CloudFormation/SAM templates, `k8s/` or `manifests/`, `charts/` / `Chart.yaml`, `wrangler.toml`, `serverless.yml`, `vercel.json`, `fly.toml`, deploy scripts.

Applies on top of core.md; the project's rules win. Find the project's own mechanism first: its secret store, its reusable workflows, its base images, its module conventions, its deploy tooling. A rule is broken when the change bypasses them or opens a hole they close. Skip what a configured linter or scanner in the repo (actionlint, hadolint, tflint, checkov, kube-linter) already enforces.

## Critical
1. **Untrusted code runs with secrets.** Mechanism: a `pull_request_target` or `workflow_run` workflow checks out the PR head (`ref: ${{ github.event.pull_request.head.sha }}` or the triggering run's artifacts) and then builds, tests or executes it; fork code runs with the base repo's secrets and a write token. The same applies to GitLab pipelines that expose protected variables to merge requests from forks. Spot: these triggers combined with checkout of PR refs, `npm install`, `make`, or running downloaded artifacts. Correct: use `pull_request` for untrusted code; if the privileged trigger is required, never run PR code in it, and split into an unprivileged build and a privileged step that only reads sanitized output.
2. **Script injection via expressions.** Mechanism: `${{ github.event.* }}` values (PR title, branch name, issue body, commit message, head ref) interpolated into a `run:` script or `actions/github-script` body are pasted as shell or JS before it runs; an attacker names a branch or title to execute commands. Spot: `${{ ... }}` of any user-controlled field inside `run:`. Correct: pass through `env:` and reference as `"$VAR"`; GitLab equivalents are `$CI_COMMIT_MESSAGE`, `$CI_MERGE_REQUEST_TITLE` used unquoted in scripts.
3. **Secrets exposed in logs or arguments.** Mechanism: a secret echoed, printed by `set -x` or debug mode, passed as a CLI argument (visible in process lists and logs), written to a file that is uploaded as an artifact, or derived and then not masked (masking covers only registered values, not transformed ones). Spot: `echo ${{ secrets.X }}`, `--password=$SECRET`, `docker login -p`, `cat .env` steps, artifact upload paths that include config files. Correct: pass via env or stdin (`--password-stdin`), mask derived values (`::add-mask::`), never upload files that hold credentials.
4. **Secrets baked into images or committed in config.** Mechanism: `ARG` / `ENV` holding tokens, or `COPY . .` without a `.dockerignore` that excludes `.env`, keys and `.git`, leaves the secret in an image layer readable by anyone who can pull it; a secret in `docker-compose.yml`, `wrangler.toml` `vars`, `serverless.yml` or `vercel.json` is committed in plain text. Spot: build args named `TOKEN`/`KEY`/`PASSWORD`, `COPY . .` with no ignore file in the diff, literal credentials in config. Correct: BuildKit secret mounts (`--mount=type=secret`), runtime env from the platform's secret store, a `.dockerignore`.
5. **Public exposure.** Mechanism: a storage bucket or container with public ACL or a policy principal of `*`, a database or admin port (22, 3389, 5432, 3306, 6379, 9200) open to `0.0.0.0/0`, a Kubernetes service of type `LoadBalancer` or an ingress for an internal tool with no auth, a public-read cloud function or queue. Spot: `acl = "public-read"`, `block_public_*` set false, `cidr_blocks = ["0.0.0.0/0"]` on non-HTTP ports. Correct: private by default, restrict to known CIDRs, a VPN or bastion for admin access, public access only behind the project's CDN pattern.
6. **Change that destroys or replaces stateful resources.** Mechanism: renaming a Terraform resource or changing an immutable attribute (engine, name, availability zone, encryption key, volume) forces replacement: the database, bucket or disk is destroyed and recreated empty. Same for Pulumi and CloudFormation replacement updates and a Helm chart that changes a StatefulSet's volume claim template or PVC name. Spot: renamed resource blocks with no `moved` block, attribute changes on databases, `force_new` fields, absent `lifecycle { prevent_destroy = true }` on new databases and buckets holding data. Correct: `moved` blocks or `state mv`, `prevent_destroy`, deletion protection and backups enabled; ask for the plan output when the diff cannot settle it.
7. **Secrets in infrastructure state or variables.** Mechanism: Terraform state and plan files contain secret values in clear text; a state backend that is local, committed or a public bucket exposes them; `*.tfvars` with real passwords committed; passwords generated in code and output without `sensitive = true`. Spot: `terraform.tfstate` or `.tfvars` in the diff, remote backend without encryption or access control, outputs of credentials. Correct: encrypted remote backend with restricted access, secrets read from the secret manager at runtime, `sensitive = true`, state files in `.gitignore`.

## High
8. **Third-party actions not pinned to a commit SHA.** Mechanism: `uses: someone/action@v3` or `@main` runs whatever the tag points to today; a compromised or retagged action executes with the job's secrets. Spot: new or changed `uses:` of a non-official action pinned to a tag or branch (include pipeline includes and orbs). Correct: full-length commit SHA with the version in a comment. Do not report version bumps of already-pinned, trusted official actions.
9. **Broad or missing workflow permissions.** Mechanism: no `permissions:` block gives the job the repository's default token scope, often read-write on everything; `write-all`, or `contents: write` / `id-token: write` on jobs that do not need them, lets any compromised step push code or mint cloud credentials. Spot: new workflows without top-level `permissions:`, broad grants at workflow level instead of job level. Correct: `permissions: {}` or `contents: read` at the top, extra scopes only on the job that needs them; OIDC with a narrowly scoped trust policy instead of long-lived cloud keys.
10. **Cache and artifact poisoning.** Mechanism: a cache written by a PR or any branch workflow and restored in a release or deploy workflow lets an attacker plant files that run later with privileges; artifacts downloaded and executed across workflows without verification; caches keyed loosely (`restore-keys` fallbacks) that mix branches. Spot: caches shared between untrusted and trusted jobs, `download-artifact` followed by execution in a privileged workflow, cache paths containing credentials or `~/.docker/config.json`. Correct: read-only caches for deploy jobs, keys including the lockfile hash and trust level, artifacts treated as data and verified.
11. **IAM wildcards and over-broad roles.** Mechanism: `Action: "*"`, `Resource: "*"`, `iam:PassRole` on all roles, administrator policies attached to a CI or workload role, trust policies without conditions (any repo, any branch can assume the role). Spot: wildcards in policy documents, missing `sub` / `aud` conditions on OIDC trust, `cluster-admin` bindings for app service accounts. Correct: enumerate the needed actions and resources, scope trust to the exact repo and branch or environment.
12. **Container runs as root or with a moving base.** Mechanism: no `USER` instruction runs the app as root, so any application bug becomes root in the container; `FROM image:latest` or an untagged base makes builds non-reproducible and silently pulls vulnerable or breaking changes; installing and running tooling in the final stage inflates the attack surface. Spot: a new Dockerfile with no `USER`, `latest` or no tag, single-stage builds shipping compilers. Correct: a non-root user, a pinned tag or digest, multi-stage build, a healthcheck where the platform relies on it for routing or restarts.
13. **Kubernetes workload without limits or with excess privilege.** Mechanism: no `resources.requests/limits` lets one pod starve a node (OOM kills of neighbors) and defeats scheduling; `privileged: true`, `hostPath`, `hostNetwork`, `allowPrivilegeEscalation`, added capabilities, or a mounted service-account token the app does not need gives a container escape path. Spot: these fields in new or changed manifests and chart values defaults. Correct: set requests and limits, `runAsNonRoot`, read-only root filesystem, drop capabilities, `automountServiceAccountToken: false` unless needed; follow the project's policy defaults.
14. **Probes that cause outages.** Mechanism: a liveness probe that checks a database or downstream service restarts every pod when that dependency is slow, turning a partial failure into a full outage; a too-short `initialDelaySeconds` or timeout kills slow-starting apps in a restart loop; no readiness probe sends traffic to pods not yet ready. Spot: liveness endpoints that call dependencies, tight thresholds in the diff. Correct: liveness checks only the process itself, readiness may check dependencies, a startup probe for slow boots.
15. **Deploy order and rollback path.** Mechanism: the pipeline runs the database migration after the new code is already serving, or runs a destructive migration in the same step as the deploy, so the new code hits the old schema (or old code hits the new one during a rolling update); no way to roll back to the previous version, or rollback that cannot work because the migration is not reversible. Spot: deploy jobs where migrate is ordered after rollout, no health-gated rollout, removed rollback steps, `latest` tags as the only version reference. Correct: backward-compatible migrations first, then rollout with health gates, previous artifact kept and addressable, manual approval for production where the project requires it. (Complements core rule 8.)

## Medium
16. **Environment config drift.** Mechanism: a setting added for staging only, or a prod value changed without the matching staging/dev change, so behavior or failures differ across environments and a bug passes staging and appears in prod; new env vars or secrets declared in one environment's config but not the others. Spot: diffs touching one of several per-environment files (`values-prod.yaml`, workspace tfvars, `[env.*]` blocks in `wrangler.toml`, per-stage serverless config). Correct: change all environments together or state why not; keep shared defaults in one base file.

## Do not report
- Formatting, ordering or naming in YAML, HCL or Dockerfiles.
- Version bumps of trusted official actions or images that are already pinned.
- Anything an enabled linter or scanner in the repo (actionlint, hadolint, tflint, checkov, kube-linter) already enforces.
- Missing `HEALTHCHECK` where the platform does not use it, or missing resource limits in clearly local-only compose files.
- `latest` tags in documentation or local development examples.
- Module structure, tool choice (Terraform vs Pulumi, Actions vs GitLab) as taste.
